# ${\color{orange}\text{HO11: Indexação Multinível}}$

A **indexação multinível** é uma técnica em que são construídos diferentes níveis de arquivos de índice sobre uma hierarquia, onde um índice de nível superior é criado para indexar o próprio arquivo de índice do nível inferior, reduzindo drasticamente o espaço de pesquisa em disco.

### ${\color{orange}\text{ Cenário de utilização }}$

* Quando a tabela de banco de dados cresce muito e o arquivo de índice de nível único também cresce (centenas ou milhares de blocos no disco) 

* Encontrar uma chave dentro desse índice de primeiro nível, depende do SGBD realizar uma busca binária que consome vários acessos de entrada e saída (I/O).

A indexação multinível resolve isso aplicando a mesma ideia do índice esparso sobre o próprio índice:

1. O **Primeiro Nível** → é o índice original que aponta para os blocos do arquivo de dados.
2. O **Segundo Nível** → é o índice esparso que aponta para os blocos de índice do primeiro nível.
3. **Níveis adicionais (terceiro, quarto, etc.)** → são adicionados até que o índice do nível mais alto ocupe exatamente 1 bloco de disco.

### ${\color{orange}\text{ Nível Único x Nível Múltiplo }}$

* **Índice de Nível Único**:
* Existe apenas um arquivo de índice entre o SGBD e o arquivo de dados.
* A pesquisa depende de fazer uma busca binária sobre os blocos do arquivo de índice.

* **Índice Multinível**:
* Elimina a necessidade de busca binária no arquivo de índice.
* O SGBD lê o único bloco do nível no topo, descobre qual bloco ler no nível intermediário e navega de cima para baixo até alcançar o arquivo de dados.
* O número de acessos a disco torna-se estritamente igual ao número de níveis da hierarquia +1 acesso ao dado real.

### ${\color{orange}\text{ Indexação Multinível Estática }}$

* **Conceito** → Compacto, sem espaço extra em blocos de índice para acomodação de novos registros. Tipicamente implementado como arquivo de índice, em que se constrói índices sobre índices.

* **Estrutura** → é altamente compacto e não deixa espaço extra livre dentro dos blocos de índice para acomodar novos registros.

* **Vantagens e Limitações** → excelente para consultas de leitura, pois não desperdiça espaço em disco. No entanto, é ineficiente diante de inserções e exclusões frequentes: inserir um novo dado no meio da tabela pode estourar a capacidade de um bloco e exigir a reestruturação física de todos os níveis acima.

* **Nível Base** → índice com valores distintos no campo de ordenação
* **Níveis Subsequentes** → índice primário sobre nível imediatamente anterior.

Derivam-se níveis de índices até que o n-ésimo nível seja armazenado em apenas um bloco.

* **Pesquisa** → complexidade logarítmica com base > 2, apenas um bloco em cada nível precisa ser acessado.

* **Base logarítmica** → fator de bloco (*F*) do índice, ou **fan-out** (*fo*)
* **Níveis (*h*)** → aproximado pela quantidade de vezes que o número de registros no nível base ($r_1$) pode ser dividido pelo fator de bloco do índice (*fo*) até resultar em 1

<div align="center">

${h \approx \left \lceil \log_{\textit{fo}}(r_1)\right \rceil}$

</div>

* **Acessos a blocos** → A = h (+ 1 acesso para recuperar o registro no arquivo indexado)

* **Alteração** → níveis ordenados, custo alto de operações de alteração do campo de indexação.

Arquivo **ISAM** (*Indexed Sequential Access Method*) é um arquivo sequencial indexado com índice multinível na **chave primária**.

#### ${\color{orange}\text{ Exemplo 1}}$

Para um arquivo indexado de Professor, com 200.000 registros de tamanho fixo de 185B, ordenado pela chave primária `CPF` e armazenado em um disco com blocos de 4KB, teremos:

* ${F = \left \lfloor \frac{4096 B}{185 B}\right \rfloor = \left \lfloor 22,14...\right \rfloor = 22}$

* ${B = \left \lceil \frac{200.000}{22}\right \rceil = \left \lceil 9.090,90...\right \rceil = 9.091}$

* ${A = \left \lceil \log_2(9.091)\right \rceil = \left \lceil 13,15...\right \rceil = 14}$

#### ${\color{orange}\text{ Exemplo 2}}$

Para Professor como sendo um arquivo **ISAM**, com `CPF` de 11B, e ponteiro de bloco ocupando 16B, teremos:

* ${F_M = \left \lfloor \frac{4096 B}{27 B}\right \rfloor = \left \lfloor 151,70...\right \rfloor = 151}$

* ${B_{M1} = \left \lceil \frac{9091}{151}\right \rceil = \left \lceil 60,20...\right \rceil = 61}$

* ${B_{M2} = \left \lceil \frac{61}{151}\right \rceil = \left \lceil 0,40...\right \rceil = 1}$

* ${A = h + 1 \approx \left \lceil \log_{151}(9.091)\right \rceil + 1 = \left \lceil 1,81... \right \rceil + 1 = 2 + 1 = 3}$

Observe que *h* deu exatamente 2, que é o número de níveis de indexação, resultando em 3 acessos totais de operações I/O.

### ${\color{orange}\text{ Indexação Multinível Dinâmica }}$

* **Conceito** → flexível, a estrutura se adapta automaticamente à medida que os dados são inseridos, alterados ou removidos, garantindo eficiência nas operações de manutenção.

* **Estrutura** → deixa espaço para alocação dinâmica de registros nos nós da estrutura.

* **Implementação**: é tipicamente implementada por meio de estruturas baseadas em árvores de pesquisa de múltiplos caminhos com restrições de balanceamento, como a Árvore B e a Árvore B+.

* **Princípio de funcionamento** → quando um nó (bloco) fica cheio durante uma inserção, a árvore realiza uma operação chamada divisão de nó (*node split*) e reorganiza os ponteiros dos níveis superiores automaticamente, mantendo a árvore sempre balanceada e com tempos de busca previsíveis.

#### ${\color{orange}\text{ Estruturas de Árvore }}$

* **Árvore (Tree)** → estrutura hierárquica de nós (elementos) conectados

	* **Raiz** → nó sem pai, de nível zero (primeiro nó da árvore)

    * **Folha** → nó sem filhos (últimos nós)

    * **Nó interno** → entre a raíz e as folhas

    * **Nível de um nó** → é o nível do seu pai mais +1

	* **Subárvore** → árvore formada por um nó e todos os seus descendentes (recursão)

### ${\color{orange}\text{ Métodos de Indexação Multinível Dinâmica }}$

* **Árvore de busca de múltiplos caminhos (*m-way*)** → Generalização da árvore de busca binária.

* Cada nó tem *m* filhos

	* Cada nó contém *m − 1* elementos (multiplicidade)

    * *h ≤ n ≤ m<sup>h</sup> −1*, onde *h* = altura e *n* = número de nós.

    * Balanceamento → ${h \approx \left \lceil \log_m(n)\right \rceil}$

* Número máximo de filhos para cada nó

    * ${t}$ → tamanho do bloco no disco (*bytes*)

    * ${m}$ → número máximo de filhos

    * ${E_n}$ → tamanho do elemento (índice + ponteiro p/ registro)

    * ${P_n}$ → tamanho do ponteiro para um nó da Árvore B

    * ${S_n}$ → espaço total de um registro nó

    * ${t \geq S_n}$ → o registro de nó não pode ser maior que o tamanho do bloco

Dessa forma:

<div align="center">

${t \geq (m-1) \times E_n + m \times P_n}$

$m \leq \frac{t + E_n}{E_n + P_n}$

${m = \left \lfloor \frac{t + E_n}{E_n + P_n} \right \rfloor}$

</div>

Outra alternativa, isolando o termo *(m - 1)*:

<div align="center">

${(m - 1) = \left \lfloor \frac{t - P_n}{E_n + P_n} \right \rfloor}$

</div>

### ${\color{orange}\text{ B-Tree }}$

* Baseada em *m-way* com restrições que tornam busca e atualização muito eficientes

    * O nó da raíz precisa ter pelo menos dois filhos

    * Nó interno tem ao menos ${\left \lceil m/2 \right \rceil}$ filhos

    * Todos os nós folhas estão no mesmo nível

Quando os **nós estão parcialmente cheios**, com cerca de 69% e a árvore está estabilizada:

* **Fator de blocagem** → ${F_B = \left \lceil (m-1) \times 0,69\right \rceil}$

* **Pesquisa** → eficiente, poucos níveis e perfeitamente balanceada

* **Alteração** → eficiente, espaço para acomodar novos registros

* Ideal para armazenamento em memória secundária

Estrutura:

* Tipicamente configurada para que um nó ocupe um bloco em disco

* **Elemento** → Campo de indexação + ponteiro de bloco (Δ) 

* Nó com ***m* ponteiros** (filhos) para nós (•), sendo um para cada filho

#### ${\color{orange}\text{ Exemplo com Árvore B }}$

Considere um arquivo de Professor, com índice *B Tree* em `Departamento` de 8B, com um nó ocupando um bloco de disco, ponteiro de nó de 12B e ponteiro de bloco de 16B.

* Uma Árvore B é uma estrutura de índice dinâmico em que **cada nó da árvore ocupa exatamente 1 bloco de disco** (no caso, 4KB = 4096B).

Para entender o exemplo, primeiro é preciso compreender o que fica guardado dentro desse único bloco/nó:

1. Elementos (**24B**) → A chave de busca (`Departamento` de 8B) + o ponteiro que indica onde o registro real do professor está no arquivo de dados 16B.

2. Ponteiros de *Nós Filhos* (**12B**) → Ponteiros que levam para outros nós da própria árvore nos níveis inferiores.

    * Um nó possui *m* filhos, ou seja, *m* ponteiros para nós filhos, logo, este tem espaço para *(m - 1)* elementos.

* **Limite do bloco da Árvore B** 

    * ${t = 4096B}$

    * ${E_n = 24B}$

    * ${P_n = 12B}$

    * ${4096B \geq (m-1) \times 24B + m \times 12}$

    * ${m = \left \lfloor \frac{4096B + 24B}{24B + 12B} \right \rfloor = \left \lfloor 114,44...\right \rfloor = 114}$

        * Então o número máximo de filhos que cada nó pode ter é 114.
        * E o número máximo de elementos *(m - 1)* é 113.

* **Altura da Árvore**

    * Supondo 200.000 registros, estes serão divididos de 114 em 114 nós, até que sobre apenas 1 registro, logo o núero de níveis, ou blocos de índice, será:
        -  ${h = \left \lceil \log_{114}(200.000)\right \rceil = \left \lceil 2,57...\right \rceil = 3}$

* **Considerando uma ocupação de nós em 69%**

    * **Fator de bloco** → ${F_B = \left \lceil 113 \times 0,69\right \rceil = \left \lceil 77,97\right \rceil = 78}$

    * **Boloco** → ${B_B = \left \lceil \frac{200.000}{78}\right \rceil = \left \lceil 2.564,10...\right \rceil = 2.565}$

    * **Espaço** → ${S_B = 2.565 \times 4Kb = 10.260KB \approx 10,01MB}$

    * **Número de acessos por pesquisa** → ${A_B = h + 1 = 3 + 1 = 4}$

### ${\color{orange}\text{ B+ Tree }}$

* Extensão B Tree com restrições que tornam ainda mais eficientes a busca e a remoção

    * **Nó Índice** → raiz ou interno que armazena exclusivamente uma chave

    * **Nó Registro** → folha que armazena registro de índice

    * Nós folha em lista encadeada ordenada

    * A ideia central da Árvore B+ é a separação total entre roteamento e dados.

* Enquanto na Árvore B tradicional os dados (ou ponteiros para o arquivo de dados) ficam espalhados por todos os nós da árvore, na Árvore B+ os nós possuem papéis bem definidos:

    1. **Nós Internos** (Nós de Rroteamento):

        * Guardam apenas chaves de busca e ponteiros para **nós filhos**.

        * Não contêm ponteiros para o arquivo de dados.

        * Sua única função é servir como "placas de sinalização" para guiar a busca até o nível inferior.

    2. **Nós Folha** (Nós de Dados/Índice):

        * Guardam todas as chaves de busca juntamente com os ponteiros para os **registros de dados reais**.

        * São conectados entre si por ponteiros adjacentes, formando uma lista encadeada (*Sequence Set*).

* **Maior Ordem *m* nos Nós Internos** → Como os nós internos da Árvore B+ não precisam guardar os ponteiros para o arquivo de dados 16B, o tamanho do elemento dentro do nó interno cai significativamente.

* **Eficiência Imbatível em Consultas por Intervalo** 

    * Ex.: `SELECT * FROM PROFESSOR WHERE DEPARTAMENTO BETWEEN 10 E 50`

    * **Na Árvore B**: O banco precisa buscar o 10, subir para o pai, buscar os intermediários, descer para o filho do meio, subir de novo (muitas navegações aleatórias na árvore).

    * **Na Árvore B+**: O banco faz a busca pela chave 10 até a folha em ${O(\log_m n)}$ e, a partir dali, apenas lê horizontalmente a lista encadeada até encontrar o 50 (leitura sequencial pura em disco).

#### Principais divergências entre Árvore B e Árvore B+

<center>

| Característica | Árvore B | Árvore B+| 
|:-|:-:|:-:|
| **Localização dos Dados** | Em todos os nós (raiz, internos e folhas).| Apenas nos nós folha. |
| **Ponteiros de Dados no Nó Interno** | Presentes 16B por elemento no nosso exemplo). | Ausentes (o nó interno guarda só a chave de 8B). | 
| **Capacidade do Nó Interno (*m*)** | Menor (o ponteiro de dados ocupa espaço no bloco). | Muito maior (sobra mais espaço para chaves/ponteiros).
| **Caminho da Busca** | Pode terminar na raiz ou em um nó interno. | Sempre vai até a folha (tempo de resposta constante). | 
| **Busca por Intervalo (*Range Query*)** | Lenta (exige navegar subindo e descendo na árvore). | Extremamente rápida (varre a lista encadeada das folhas). | 
|**Duplicação de Chaves** | Não há (cada chave aparece só uma vez). | Chaves nos nós internos são duplicadas no nó folha. |

</center>

#### ${\color{orange}\text{ Exemplo com Árvore B+ }}$

Arquivo de Professor, com índice B+ Tree em `Departamento` de 8B, com um nó ocupando um bloco de disco, ponteiro de nó de 12B, ponteiro de bloco de 16B.

#### Nó Índice

* ***Tamanho do elemento***

    * ${E_{ni} = 8B}$

* ***Limite do bloco***

    * ${4096B \geq  (m - 1) \times 8B + m \times 12B}$
    
    * chave/índice 8B + ponteiro para nó (12B)

* ***Máximo de nós por bloco***

    * ${m = \left \lfloor \frac{4096B + 8B}{8B + 12B}\right \rfloor = \left \lfloor 205,2\right \rfloor = 205}$

    * Equivale à ordem da árvore.

* ***Máximo de elementos por bloco***

    * ${(m - 1) = 205 - 1 = 204}$

* ***Altura da árvore***

    * ${h = \left \lceil \log_{205}(200.000)\right \rceil = \left \lceil 2,29...\right \rceil = 3}$

* ***Altura Nós Índices***

    * ${h_i = h -1 = 3 - 1 = 2}$

#### Nó Registro

* ***Tamanho do elemento***

    * ${E_{nr} = (8B + 16B) = 24B}$

* ***Limite do bloco***

    * ${4096B \geq  (m - 1) \times 24B + 12B}$

    * chave/índice (8B) + ponteiro para registro (16B) + **1 ponteiro** para o próximo nó (12B) da lista encadeada de folhas

    * fica mais fácil isolar o termo *(m - 1)*

<div align="center">

${t \geq (m - 1) \times E_n + P_n}$

${(m - 1) = \left \lfloor \frac{t - P_n}{E_n}\right \rfloor}$

</div>

* ***Elementos por bloco***

    * ${(m - 1) = \left \lfloor \frac{4096B - 12B}{24B}\right \rfloor = \left \lfloor 170,16...\right \rfloor = 170}$

#### Considerando uma ocupação de nós em 69%

* **Fator de Bloco (índice)** → ${F_{iB+} = \left \lceil 204 \times 0,69\right \rceil = \left \lceil 140,76\right \rceil = 141}$

    * Média de ponteiros úteis por bloco

* **Fator de Bloco (registro)** → ${F_{rB+} = \left \lceil 170 \times 0,69\right \rceil = \left \lceil 117,7\right \rceil = 118}$

* **Blocos** → ${B_{B+} = \left \lceil \frac{200.000}{118}\right \rceil = \left \lceil 1.694,91...\right \rceil = 1.695}$

* **Nível** 0 a ${(h_i - 1)}$ → total de nós (blocos) internos necessários para montar a estrutura de roteamento (1.695 ponteiros), sem os nós folha

    * Capacidade Efetiva por Nó Interno (ponteiros/blocos) → ${F_{iB+} + h_i = 141 + 2 = 143}$
        - O ajuste ${+ h_i}$ é uma correção para contabilizar a acumulação de nós nos níveis superiores (raiz e níveis intermédios) sem ter de somar cada nível individualmente.

    * Nó → Bloco → ${\left \lceil \frac{1.695}{143}\right \rceil = \left \lceil 11,83...\right \rceil = 12}$

* **Espaço** → ${S_{B+} = (1.695 + 12) \times 4KB = 6.828KB \approx 6,67MB}$

* Acessos em pesquisa → ${A_{B+} = h = 3}$ + 1 acesso para recuperar o registro no arquivo indexado
