### ${\color{orange}\text{ Operações de conjuntos em SQL }}$

As operações de conjunto (*Set Operations*) no SQL permitem combinar os resultados de duas ou mais consultas `SELECT` em um único conjunto de dados. Diferente dos `JOIN`s (que combinam colunas na horizontal), as operações de conjunto combinam linhas na vertical.

Para utilizar qualquer operação de conjunto, as consultas envolvidas precisam atender a duas condições obrigatórias:

1. **Mesmo número de colunas**: Ambas as consultas devem retornar a mesma quantidade de projeções.

2. **Tipos de dados compatíveis**: Os tipos de dados das colunas correspondentes devem ser do mesmo tipo ou conversíveis entre si (ex: VARCHAR com VARCHAR, INT com INT).

### ${\color{orange}\text{ 1. UNION (União) }}$

Combina todas as linhas retornadas por duas ou mais consultas.

* **UNION (Padrão)**: Combina os resultados e remove linhas duplicadas (realiza um processo interno de ordenação/deduplicação).

* **UNION ALL**: Combina os resultados e mantém todas as duplicadas. É significativamente mais rápido por não gastar processamento removendo duplicatas.

**Exemplo**:

Quando você precisa consolidar dados semelhantes vindos de tabelas diferentes ou com condições de filtro distintas.

```SQL
-- Lista única de todos os e-mails para envio de comunicação (clientes e fornecedores)
SELECT email FROM clientes
UNION
SELECT email FROM fornecedores;
```

### ${\color{orange}\text{ 2. INTERSECT (Interseção) }}$

Retorna apenas as linhas que estão presentes no resultado de ambas as consultas (elementos em comum). Por padrão, também remove duplicatas.

**Exemplo**:

Quando você quer encontrar registros que atendem simultaneamente a dois critérios que estão estruturados em consultas ou tabelas separadas.

```SQL
-- Encontrar clientes que também são cadastrados como fornecedores
SELECT email FROM clientes
INTERSECT
SELECT email FROM fornecedores;
```

### ${\color{orange}\text{ 3. EXCEPT / MINUS (Diferença) }}$

Retorna as linhas presentes na primeira consulta que não aparecem na segunda consulta.

>No **PostgreSQL**, **SQL Server** e **SQLite** utiliza-se `EXCEPT`. No **Oracle**, utiliza-se `MINUS`.

**Exemplo**:

Para identificar ausências, pendências ou realizar checagem de exceções/lacunas entre conjuntos de dados.

```SQL
-- Clientes que realizaram compras, mas nunca registraram um suporte/reclamação
SELECT id_cliente FROM vendas
EXCEPT
SELECT id_cliente FROM suportes;
```

### ${\color{orange}\text{ CTE — Common Table Expression }}$

Em vez de aninhar uma subconsulta dentro da outra, você pode isolar cada subconsulta no topo do código dando um nome para ela, como se fosse uma tabela temporária.

**Exemplo**:

```SQL
WITH FilmesComNotaAlta AS (
    SELECT id, name 
    FROM movies 
    WHERE rank > 8
),
AtoresEFilmes AS (
    SELECT actor_id, movie_id 
    FROM roles
)

SELECT A.first_name, F.name
FROM FilmesComNotaAlta AS F
JOIN AtoresEFilmes AS AF ON F.id = AF.movie_id
JOIN actors AS A ON A.id = AF.actor_id;
```

A CTE é considerada uma excelente prática no mercado e no desenvolvimento de software moderno.

Os otimizadores de consultas (*Query Optimizers*) interpretam a CTE e a subconsulta aninhada da mesma forma. Eles transformam ambas em uma mesma estrutura lógica e aplicam as mesmas otimizações (como o *predicate pushdown*).

Ele simplesmente resolve a expressão em memória no momento da execução, exatamente como faria com um (`SELECT` ...) no `FROM`.

Antigamente, o PostgreSQL tratava toda CTE como uma "barreira de otimização" (materializando o resultado temporariamente). Desde o PostgreSQL 12 (lançado em 2019), o padrão passou a ser `AS MATERIALIZED` ou `AS NOT MATERIALIZED`, fazendo com que CTEs normais sejam otimizadas *inline* por padrão, sem perda de desempenho.

Além disso a utilização de CTEs garante boa legibilidade do código, manutenibilidade e reutilização de código com suporte à recursividade.

* Por ser um interpretador acadêmico focado nas operações fundamentais de álgebra relacional, o RelaX não suporta a sintaxe `WITH`. No entanto, para projetos reais e no mercado de trabalho, prefira sempre utilizar CTEs.

## ${\color{orange}\text{ Atividade do Hands-On }}$

Especificar as seguintes consultas em SQL para recuperar os dados em um banco de dados relacional, considerando o conjunto de dados (dataset) denominado [IMDB-sample](https://dbis-uibk.github.io/relax/calc/gist/41cf5ce652756d9331eec7562644e074/imdbsample/0) disponível na calculadora [RelaX](https://dbis-uibk.github.io/relax/landing):

**1. Projetar o primeiro nome e o último nome dos atores que são diretores**

Em Álgebra Relacional:

```
-- interseção do conjunto dos atores com os diretores
(π first_name, last_name (actors)) ∩ (π first_name, last_name (directors))
```

Em SQL:

```SQL
SELECT  first_name, last_name
FROM    actors
INTERSECT
SELECT  first_name, last_name
FROM    directors
```

**2. Projetar o primeiro nome e o último nome dos atores que não são diretores**

Em Álgebra Relacional:

```
-- diferença entre atores e diretores
(π first_name, last_name (actors)) - (π first_name, last_name (directors))
```

Em SQL:

```SQL
SELECT  first_name, last_name
FROM    actors
EXCEPT
SELECT  first_name, last_name
FROM    directors
```

**3. Projetar o primeiro nome e o último nome dos atores e diretores**

Em Álgebra Relacional:

```
-- atores e diretores (união)
(π first_name, last_name (actors)) ∪ (π first_name, last_name (directors))
```

Em SQL:

```SQL
SELECT  first_name, last_name
FROM    actors
UNION
SELECT  first_name, last_name
FROM    directors
```

**4. Projetar o nome dos filmes que não são dirigidos por nenhum diretor**

Em Álgebra Relacional:

```
-- filmes dirigidos (movies_directors), todos os filmes (movies)
-- filmes sem diretores movies - movies_directors
fsd = (π id (movies)) - (π movie_id (movies_directors))

-- junção natural para obter nome dos filmes e projeta os nomes
π name ( (fsd) ⨝ (movies) )

-- O problema que o resultado vai ser vazio
```

Em SQL:

```SQL
SELECT  name FROM movies
EXCEPT
SELECT  M.name 
FROM    movies AS M 
        JOIN movies_directors AS MD 
        ON M.id = MD.movie_id
```

**5. Projetar primeiro nome e o último nome dos atores que não atuaram em pelo menos dois filmes**

Em Álgebra Relacional:

```
-- número de filmes por ator
fpa = γ actor_id ; COUNT(movie_id)→nFilmes (roles)

-- atores que atuaram em pelo menos 2 filmes
adf = σ nFilmes ≥ 2 (fpa)

-- atores que não atuaram em pelo menos 2 filmes
nadf = (π id (actors)) - (π actor_id (adf))

-- obtendo os atores
a = actors ⨝ nadf

-- projetando nome e sobrenome
π first_name, last_name (a)
```

Em SQL:

```SQL
SELECT  first_name, last_name FROM actors
EXCEPT
SELECT  A.first_name, A.last_name FROM actors AS A
JOIN (
     SELECT actor_id, COUNT(movie_id) AS nFilmes
     FROM   roles GROUP BY actor_id
     HAVING nFilmes >= 2
     ) AS P
ON A.id = P.actor_id
```

**6. Projetar, por gênero e ano, o número médio de filmes com menos de dois atores atuando**

Em Álgebra Relacional:

```
-- número de atores por filme
af = γ movie_id ; COUNT(actor_id)→nAtores (roles)

-- filmes com mais de 2 atores atuando
fda = σ nAtores ≥ 2 (af)

-- filmes com menos de 2 atores atuando
fmda = (π id (movies)) - (π movie_id (fda))

-- obter filmes
f = fmda ⨝ movies

-- obter gênero
fg = (f) ⨝ id = movie_id (movies_genres)

-- projetar número de filmes por ano e gênero
γ genre, year ; COUNT(id)→nFilmes (fg)
```

Em SQL:

```SQL
SELECT MG.genre, M.year, COUNT(*) AS nFilmes
FROM (
      movies_genres AS MG
      JOIN (
            movies AS M
            JOIN (
                  SELECT id FROM movies
                  EXCEPT
                  SELECT R.movie_id
                  FROM (
                         SELECT movie_id, COUNT(*) AS nAtores
                         FROM roles GROUP BY movie_id
                         HAVING nAtores >= 2
                       ) AS R
                ) AS M2
            ON M.id = M2.id
           )
      ON MG.movie_id = M.id
     )
GROUP BY MG.genre, M.year
```
